<h3 data-ke-size="size23">개념 정립</h3>
<h4 data-ke-size="size20">Decentrailzed.</h4>
<p data-ke-size="size16">탈중앙화라는 의미로 일반적인 웹 서비스가 중앙 서버에서 운영하는 것과 별개로 Ethereum에서는 여러 노드가 같은 Blockchain 상태를 유지한다.</p>
<h4 data-ke-size="size20">Wallet</h4>
<p data-ke-size="size16">Wallet은 Ethereum Account와 Private Key를 관리하고, Transaction 서명을 도와주는 프로그램이다. Wallect안에 ETH가 들어있다고 생각하기 편하지만, ETH와 Token의 상태 자체는 Blockchain에 기록되어 있으며, Wallet은 그것을 사용할 수 있도록 키를 관리하는 프로그램에 가깝다.</p>
<p data-ke-size="size16"> </p>
<h4 data-ke-size="size20">MetaMask.</h4>
<p data-ke-size="size16">Wallet의 한 종류로 브라우저 확장 프로그램이나 모바일 앱 형태로 사용할 수 있는 Ethereum Wallet이다. 사용자가 웹사이트에서 connect Wallet 버튼을 누르면 MetaMask 창이 뜨는데, 이때 Metamask는 사용자의 이더리움 Account, Key, Signature 등을 관리하게 된다.</p>
<h4 data-ke-size="size20">dApp</h4>
<p data-ke-size="size16">dApp은 Decentralized Application의 약자이다. Ethereum의 스마트 컨트랙트를 사용하는 웹 애플리케이션을 생각하면 이해하기 쉽다. 예를 들어 사용자가 웹사이트에서</p>
<pre class="properties"><code>Connect Wallet
Swap
Mint NFT
Send Transaction</code></pre>
<p data-ke-size="size16">같은 버튼을 누르면 브라우저의 JavaScript 코드가 Ethereum과 상호작용해야 한다. 그런데 일반적인 웹 브라우저는 사용자의 Ethereum private key를 직접 가지고 있지 않아서 보통 MetaMask 같은 Wallet이 중간에서 계정을 관리하고 서명 작업을 수행한다. 전체 구조를 단순화하면 다음과 같다.</p>
<pre class="routeros"><code>dApp
  ↓
Provider
  ↓
Wallet
  ↓
Ethereum Client / RPC
  ↓
Ethereum Network</code></pre>
<p data-ke-size="size16">EIP-1193은 여기서 dApp이 사용하는 Provider의 JavaScript API를 표준화한다.</p>
<h3 data-ke-size="size23">Provider</h3>
<p data-ke-size="size16">EIP-1193에서 Provider는 Ethereum에 접근하기 위해 dApp에 제공되는 JavaScript 객체이다. Provider의 핵심 역할은 크게 두 가지이다.</p>
<pre class="angelscript"><code>1. Ethereum RPC 요청 보내기
2. Wallet / Chain 상태 변화를 dApp에 알려주기</code></pre>
<p data-ke-size="size16">예를 들어 브라우저에서 MetaMask에는 다음과 같은 코드가 있다.</p>
<pre class="css"><code>window.ethereum.request({
    method: "eth_chainId"
});</code></pre>
<p data-ke-size="size16">여기서 <code>window.ethereum</code>이 대표적인 Provider 구현 사례이다. </p>
<h3 data-ke-size="size23">RPC</h3>
<p data-ke-size="size16">RPC는 Remote Procedure Call의 약자이다. 쉽게 말하면 다른 시스템에게 &lt;<span style="letter-spacing: 0px;">이 작업을 수행하고 결과를 알려줘&gt; </span>라고 요청하는 방식이다. Ethereum에서는 예를 들어 다음과 같은 JSON-RPC method가 존재한다.</p>
<pre class="nginx"><code>eth_chainId
eth_accounts
eth_getBalance
eth_call
eth_sendTransaction</code></pre>
<p data-ke-size="size16">EIP-1193의 <code>request()</code>는 이런 RPC 요청을 Provider를 통해 전달할 수 있도록 공통 API를 제공한다.</p>
<h2 data-ke-size="size26">공식 문서 Summary</h2>
<p data-ke-size="size16">EIP-1193의 목적은 Ethereum JavaScript Provider API를 통일하여 client와 application 사이의 호환성을 높이는 것이다.</p>
<p data-ke-size="size16">과거에는 Wallet마다 Provider 인터페이스와 동작 방식이 서로 달랐다. 그러면 dApp 개발자는</p>
<pre class="properties"><code>Wallet A용 코드
Wallet B용 코드
Wallet C용 코드</code></pre>
<p data-ke-size="size16">를 따로 고려해야 할 수 있다. EIP-1193은 이를 공통 Provider 인터페이스로 추상화한다.</p>
<pre class="angelscript"><code>dApp
   ↓
EIP-1193 Provider API
   ↓
다양한 Wallet / Client</code></pre>
<h3 data-ke-size="size23">그렇다면 EIP-1193은 왜 만들어졌을까?</h3>
<p data-ke-size="size16">Ethereum dApp에서 Wallet과 통신하는 방식은 매우 중요하다. 사용자가 NFT를 구매하거나 토큰을 전송하거나 스마트 컨트랙트를 호출하려면 결국 Wallet과 연결되어야 한다. 하지만 Provider 구현마다 서로 다른 API와 동작을 사용한다면 dApp의 호환성이 크게 떨어진다. 예를 들어 다음과 같은 상황을 생각할 수 있다.</p>
<pre class="properties"><code>Wallet A → provider.send(...)
Wallet B → provider.sendAsync(...)
Wallet C → 다른 방식</code></pre>
<p data-ke-size="size16">dApp 입장에서는 Wallet마다 별도의 로직을 작성해야 한다. 또한 계정이나 네트워크가 변경되었을 때 어떤 이벤트를 발생시킬지도 통일되어 있지 않으면 복잡해진다. EIP-1193은 이 문제를 해결하기 위해 Provider를</p>
<pre class="properties"><code>minimal
event-driven
transport agnostic
RPC protocol agnostic</code></pre>
<p data-ke-size="size16">한 인터페이스로 정의했다. 즉 Provider가 내부적으로 HTTP를 사용하든 WebSocket을 사용하든, 어떤 Wallet 구조를 사용하든 dApp이 바라보는 인터페이스를 최대한 단순하게 유지하려는 것이다.</p>
<h3 data-ke-size="size23">EIP-1193의 핵심 - request()</h3>
<p data-ke-size="size16">EIP-1193에서 가장 중요한 API는 <code>request()</code>이다. 공식 인터페이스를 단순화하면 다음과 같다.</p>
<pre class="cs"><code>interface RequestArguments {
    readonly method: string;
    readonly params?: readonly unknown[] | object;
}

Provider.request(args: RequestArguments): Promise&lt;unknown&gt;;</code></pre>
<p data-ke-size="size16">즉 dApp은 Provider에게 무슨 Method를 호출할지와 필요하다면 어떤 Params를 전달할지를 보낸다.</p>
<p data-ke-size="size16"> </p>
<h2 data-ke-size="size26">그러면.. 계정 연결은 어떻게 이루어질까?</h2>
<p data-ke-size="size16">MetaMask를 사용하는 dApp에서 흔히 다음 코드를 볼 수 있다.</p>
<pre class="dart"><code>const accounts = await window.ethereum.request({
    method: "eth_requestAccounts"
});</code></pre>
<p data-ke-size="size16">사용자가 아직 사이트에 계정 접근을 허용하지 않았다면 MetaMask에서 연결 승인 창이 나타난다. 사용자가 승인하면 dApp은 허용된 account 정보를 전달받는다. 전체 흐름은 대략 다음과 같다.</p>
<pre class="routeros"><code>dApp
 │
 │ eth_requestAccounts
 ▼
EIP-1193 Provider
 │
 ▼
Wallet
 │
 │ 사용자에게 승인 요청
 ▼
User
 │
 │ 승인
 ▼
Wallet
 │
 ▼
Account Address 반환</code></pre>
<p data-ke-size="size16">여기서 주의할 점은 <code>eth_requestAccounts</code>라는 RPC method 자체가 EIP-1193의 핵심 API인 것은 아니라는 것이다.</p>
<p data-ke-size="size16">EIP-1193이 표준화한 핵심은</p>
<pre class="css"><code>provider.request(...)</code></pre>
<p data-ke-size="size16">라는 호출 인터페이스이다. 그 안에서 어떤 RPC method를 호출하는지는 별도의 RPC/EIP 명세가 정할 수 있다.</p>
<h2 data-ke-size="size26">Promise와 Error</h2>
<p data-ke-size="size16"><code>request()</code>는 Promise를 반환한다. 요청에 성공하면 결과가 resolve되고, 실패하면 <code>ProviderRpcError</code> 형태로 reject된다.</p>
<pre class="angelscript"><code>interface ProviderRpcError extends Error {
    code: number;
    data?: unknown;
}</code></pre>
<p data-ke-size="size16">EIP-1193은 대표적으로 다음 Provider error code를 정의한다.</p>
<table data-ke-align="alignLeft">
<thead>
<tr>
<th>Code</th>
<th>의미</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>4001</code></td>
<td>사용자가 요청을 거절함</td>
</tr>
<tr>
<td><code>4100</code></td>
<td>해당 method/account에 대한 권한이 없음</td>
</tr>
<tr>
<td><code>4200</code></td>
<td>Provider가 해당 method를 지원하지 않음</td>
</tr>
<tr>
<td><code>4900</code></td>
<td>모든 chain과 연결이 끊김</td>
</tr>
<tr>
<td><code>4901</code></td>
<td>요청 대상 chain과 연결되어 있지 않음</td>
</tr>
</tbody>
</table>
<p data-ke-size="size16">예를 들어 사용자가 Wallet에서 Transaction 서명을 거절했다면 dApp은 단순히 실패로만 처리하는 것이 아니라, Error Code를 보고 사용자가 직접 거절했다는 것을 구분할 수 있다.</p>
<h3 data-ke-size="size23">Event가 필요한 이유</h3>
<p data-ke-size="size16">Blockchain dApp의 상태는 계속 바뀔 수 있다. 예를 들어 사용자가 MetaMask에서 계정을 바꿀 수 있다.</p>
<pre class="properties"><code>Account A
   ↓
Account B</code></pre>
<p data-ke-size="size16">또는 Ethereum Mainnet에서 다른 네트워크로 바꿀 수도 있다.</p>
<pre class="nginx"><code>Ethereum Mainnet
      ↓
Arbitrum</code></pre>
<p data-ke-size="size16">그런데 dApp이 이 변화를 모르고 예전 account나 chain을 기준으로 동작하면 문제가 발생할 수 있으니 EIP-1193은 Event 기반 API를 정의한다. Provider는 Node.js <code>EventEmitter</code> 방식의 removeListener를 제공해야 하며 대표적인 Event는 다음과 같다</p>
<pre class="arduino"><code>connect
disconnect
chainChanged
accountsChanged
message</code></pre>
<p data-ke-size="size16"> </p>
<h4 data-ke-size="size20">accountsChanged</h4>
<pre class="angelscript"><code>기존 Account
0xAAAA...
      ↓
MetaMask에서 계정 변경
      ↓
accountsChanged
      ↓
새 Account
0xBBBB...</code></pre>
<p data-ke-size="size16">이 이벤트를 처리하지 않으면 화면에는 기존 사용자의 잔액이나 정보가 계속 표시될 수 있다.</p>
<h4 data-ke-size="size20">chainChanged</h4>
<pre class="routeros"><code>Ethereum Mainnet
chainId = 0x1
       ↓
Network 변경
       ↓
다른 EVM Chain</code></pre>
<p data-ke-size="size16">같은 contract address처럼 보이더라도 chain이 다르면 완전히 다른 contract일 수 있기 때문에 중요하다.</p>
<h4 data-ke-size="size20">connect / disconnect</h4>
<p data-ke-size="size16">Provider가 chain에 RPC 요청을 처리할 수 있게 되면 <code>connect</code> 이벤트를 사용할 수 있고, 어떤 chain에도 요청을 처리할 수 없는 상태가 되면 <code>disconnect</code>가 발생한다. 여기서 Wallet에 계정을 연결했다라는 의미의 connect와 EIP-1193에서 말하는 connectivity를 혼동하면 안 된다.</p>
<p data-ke-size="size16">EIP-1193에서 Provider가 connected라는 것은 적어도 하나의 Chain에 RPC Request를 정상적으로 전달하고, response를 받을 수 있다는 의미이다.</p>
<h4 data-ke-size="size20">실제 사용 사례 - MetaMask</h4>
<p data-ke-size="size16">EIP-1193의 가장 이해하기 쉬운 실제 구현 사례가 MetaMask이다. 현재 MetaMask 공식 개발자 문서에서도 Ethereum Provider API가 EIP-1193 표준을 따른다고 명시하고 있다. MetaMask Provider는 다음과 같은 EIP-1193 형태를 제공한다.</p>
<pre class="stylus"><code>request()
accountsChanged
chainChanged
connect
disconnect
message</code></pre>
<p data-ke-size="size16"> </p>
<h4 data-ke-size="size20">MeteMask의 간단한 정리.</h4>
<p data-ke-size="size16">사용자가 dApp에서 Connect Wallet을 누른다고 해보자.</p>
<pre class="angelscript"><code>사용자
  │
  │ Connect Wallet 클릭
  ▼
dApp
  │
  │ provider.request(...)
  ▼
EIP-1193 Provider
  │
  ▼
MetaMask
  │
  │ 사용자 승인 요청
  ▼
사용자 승인
  │
  ▼
Account 정보 반환</code></pre>
<p data-ke-size="size16">이후 사용자가 MetaMask에서 다른 account로 변경하면</p>
<pre class="properties"><code>MetaMask account 변경
        ↓
accountsChanged Event
        ↓
dApp Event Handler
        ↓
화면의 Account / Balance 갱신</code></pre>
<p data-ke-size="size16">Network를 변경하면</p>
<pre class="properties"><code>Network 변경
     ↓
chainChanged Event
     ↓
dApp에서 새로운 chain 확인</code></pre>
<p data-ke-size="size16">이 된다.</p>

<h2 data-ke-size="size26">정리</h2>
<p data-ke-size="size16">EIP-1193은 새로운 token이나 새로운 transaction type을 정의하는 EIP가 아니다.</p>
<p data-ke-size="size16">dApp이 Ethereum Wallet 및 Client와 상호작용할 때 사용할 Provider JavaScript API를 표준화한 Interface EIP이다.</p>
<p data-ke-size="size16">핵심은 다음과 같다.</p>
<pre class="stylus"><code>request()
→ RPC request를 일관된 형태로 호출

ProviderRpcError
→ 요청 실패 이유를 표준적인 형태로 전달

accountsChanged
→ 사용 가능한 Account 변경 감지

chainChanged
→ 연결된 Chain 변경 감지

connect / disconnect
→ Provider의 chain connectivity 변화 감지</code></pre>
<p data-ke-size="size16">과거 Wallet Provider마다 서로 다른 API를 제공하면서 발생하던 호환성 문제를 줄이고, dApp이 공통된 인터페이스를 통해 여러 Wallet과 상호작용할 수 있도록 만들었다. 실제로 MetaMask의 현재 Provider API도 EIP-1193을 따르고 있으며 <code>request()</code>, <code>accountsChanged</code>, <code>chainChanged</code> 같은 인터페이스를 제공한다.</p>
