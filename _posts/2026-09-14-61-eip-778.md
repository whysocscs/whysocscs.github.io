<h2 data-ke-size="size26">필수 개념</h2>
<h3 data-ke-size="size23">노드(Node)</h3>
<p data-ke-size="size16">이더리움 네트워크에 참여하는 하나의 컴퓨터 또는 프로그램 인스턴스를 노드라고 한다.</p>
<p data-ke-size="size16">노드는 다른 노드와 연결하여 블록이나 트랜잭션 같은 데이터를 주고받는다. 이더리움은 중앙 서버 한 대가 모든 데이터를 전달하는 구조가 아니기 때문에, 각 노드는 네트워크에 존재하는 다른 노드를 발견하고 연결해야 한다.</p>
<p data-ke-size="size16">즉 다음과 같은 과정이 필요하다.</p>
<pre class="routeros"><code>새로운 Ethereum Node 실행
        ↓
다른 Node를 발견
        ↓
상대 Node의 IP / Port 등의 정보 확인
        ↓
P2P 연결
        ↓
Ethereum 데이터 교환</code></pre>
<h3 data-ke-size="size23">P2P</h3>
<p data-ke-size="size16">P2P는 Peer-to-Peer의 약자이다.</p>
<p data-ke-size="size16">일반적인 웹 서비스에서는</p>
<pre class="arduino"><code>Client
   ↓
Server</code></pre>
<p data-ke-size="size16">처럼 중앙 서버가 존재하지만 P2P 네트워크에서는 여러 참여자가 서로 직접 연결된다.</p>
<pre class="crmsh"><code>Node A ───── Node B
  │           │
  │           │
Node C ───── Node D</code></pre>
<p data-ke-size="size16">Ethereum도 이런 P2P 네트워크를 기반으로 동작한다.</p>
<p data-ke-size="size16">따라서 노드가 네트워크에 처음 참여하면 가장 먼저 발생하는 질문이 있다. 나는 다른 Ethereum 노드를 어떻게 찾는가?</p>
<p data-ke-size="size16">이를 위해 Ethereum에는 Node Discovery Protocol이 존재한다.</p>
<h3 data-ke-size="size23">Node Discovery</h3>
<p data-ke-size="size16">Node Discovery는 Ethereum 노드가 서로의 존재와 연결 정보를 알아내기 위한 프로토콜이다.</p>
<p data-ke-size="size16">Geth 문서에 따르면 Geth는 충분한 수의 peer를 확보할 때까지 discovery protocol을 이용해 다른 노드를 계속 찾는다. 새로운 노드는 처음에는 bootstrap node를 통해 다른 peer들을 소개받고, 이후 discovery를 통해 네트워크의 다른 노드를 알아간다.</p>
<p data-ke-size="size16">그런데 다른 노드에 연결하려면 최소한 다음과 같은 정보가 필요하다.</p>
<pre class="routeros"><code>Node의 공개키
IP Address
TCP Port
UDP Port</code></pre>
<p data-ke-size="size16">기존 Node Discovery v4에서는 전달할 수 있는 정보의 종류가 제한적이었다.</p>
<p data-ke-size="size16">바로 이 문제를 개선하기 위해 나온 것이 EIP-778의 Ethereum Node Record(ENR) 이다.</p>
<h2 data-ke-size="size26">공식 문서 Simple Summary</h2>
<p data-ke-size="size16">EIP-778은 Ethereum P2P 네트워크에서 노드의 연결 정보를 표현하기 위한 Ethereum Node Record(ENR) 형식을 정의한다.</p>
<p data-ke-size="size16">쉽게 말하면 하나의 Ethereum 노드가</p>
<p data-ke-size="size16"> </p>
<p data-ke-size="size16">나는 누구이고, <br/>어떤 주소에 있으며, <br/>어떤 방식으로 연결할 수 있는가</p>
<p data-ke-size="size16"> </p>
<p data-ke-size="size16">를 표현하는 표준화된 레코드라고 볼 수 있다.</p>
<h2 data-ke-size="size26">Abstract</h2>
<p data-ke-size="size16">EIP-778은 P2P 연결 정보를 저장할 수 있는 개방형 형식인 Ethereum Node Record를 정의한다. ENR은 크게 다음 정보로 구성된다.</p>
<pre class="fortran"><code>signature
sequence number
key/value pairs</code></pre>

<p data-ke-size="size16">중요한 점은 IP와 Port만 고정적으로 저장하는 형식이 아니라 확장 가능한 key/value 구조라는 것</p>
<hr data-ke-style="style1">
<h2 data-ke-size="size26">그렇다면 EIP-778은 왜 만들어졌을까?</h2>
<p data-ke-size="size16">기존 Ethereum Node Discovery v4에서는 노드가 전달할 수 있는 정보가 제한되어 있었다. 기본적으로 노드 공개키, IP, TCP Port, UDP Port 정도를 전달할 수 있었고 새로운 종류의 연결 정보나 프로토콜 관련 데이터를 유연하게 추가하기 어려웠다.</p>
<p data-ke-size="size16">하지만 네트워크 프로토콜은 시간이 지나면서 계속 변화할 수 있으며 IPv6 정보가 필요하거나 노드가 추가적인 네트워크 기능을 알려야 할 수도 있다. 또한 기존 구조처럼 전달할 정보가 고정되어 있으면 프로토콜을 확장하기 어려워지며 EIP-778은 이를 해결하기 위해 노드 정보를 key/value  기반의 확장 가능한 record로 만들었다.</p>
<p data-ke-size="size16"> </p>
<p data-ke-size="size16">정리하면 기존 방식에는 크게 다음 문제가 있었다.</p>
<ol data-ke-list-type="decimal" style="list-style-type: decimal;">
<li>전달 가능한 노드 정보의 종류가 제한적이었다.</li>
<li>새로운 네트워크 기능을 추가하기 어려웠다.</li>
<li>노드의 IP나 Port가 변경되었을 때 어느 정보가 최신인지 판단할 방법이 필요했다.</li>
<li>전달받은 노드 정보가 실제 해당 노드가 만든 것인지 검증할 필요가 있었다.</li>
</ol>
<p data-ke-size="size16">EIP-778은 이 문제를 각각</p>
<pre class="fortran"><code>확장 가능한 key/value
sequence number
signature</code></pre>
<p data-ke-size="size16">로 해결한다.</p>
<h2 data-ke-size="size26">ENR의 구조</h2>
<p data-ke-size="size16">EIP-778에서 ENR은 기본적으로 다음 구조를 가진다.</p>
<pre class="json"><code>[signature, seq, k, v, k, v, ...]</code></pre>
<p data-ke-size="size16">예를 들어 개념적으로 다음과 같은 레코드라고 생각할 수 있다.</p>
<pre class="ini"><code>signature = ...
seq       = 5

id        = v4
ip        = 203.0.113.10
tcp       = 30303
udp       = 30303
secp256k1 = Public Key</code></pre>
<p data-ke-size="size16">여기서 중요한 요소를 하나씩 살펴보자.</p>
<h3 data-ke-size="size23">1. signature</h3>
<p data-ke-size="size16">ENR에는 전자서명이 포함된다. 그러면, 왜 서명이 필요할까? 공격자가 다른 노드의 정보를 마음대로 다음처럼 위조할 수 있다고 가정해보자.</p>
<pre class="routeros"><code>Node A의 공개키
        +
공격자의 IP Address</code></pre>
<p data-ke-size="size16">이런 잘못된 정보가 네트워크에 퍼지면 노드들은 올바르지 않은 endpoint로 연결을 시도할 수 있다. 그래서 ENR은 record 내용에 대한 서명을 포함한다. 기본 <code>v4</code> identity scheme에서는 record의 내용을 Keccak-256으로 해시한 후 secp256k1 키를 이용해 서명하며, 검증자는 ENR 안의 공개키를 이용해 해당 서명을 검증할 수 있다.</p>
<p data-ke-size="size16">개념적으로 보면 다음과 같다.</p>
<pre class="crmsh"><code>ENR Content
    ↓
Keccak-256
    ↓
Node Private Key로 Signature 생성
    ↓
ENR에 Signature 포함</code></pre>
<p data-ke-size="size16">다른 노드는</p>
<pre class="crmsh"><code>ENR 수신
   ↓
Signature 검증
   ↓
올바른 Node가 만든 Record인지 확인</code></pre>
<p data-ke-size="size16">할 수 있다.</p>
<p data-ke-size="size16">즉 signature는 ENR의 무결성과 노드 identity에 대한 검증 수단이다.</p>
<h2 data-ke-size="size26">2. seq - Sequence Number</h2>
<p data-ke-size="size16">ENR에는 <code>seq</code>라는 64-bit unsigned integer가 존재한다. 이 값은 어떤 ENR이 더 최신 정보인지 판단하기 위해 사용된다.</p>
<p data-ke-size="size16">예를 들어 Node A가 처음 다음 주소를 사용하고 있다고 해보자.</p>
<pre class="routeros"><code>seq = 10
ip  = 1.1.1.1</code></pre>
<p data-ke-size="size16">그런데 Node A의 IP가 변경되었다. 그러면 Node A는 새로운 ENR을 만들면서 sequence number를 증가시킨다.</p>
<pre class="routeros"><code>seq = 11
ip  = 2.2.2.2</code></pre>
<p data-ke-size="size16">다른 노드가 두 ENR을 모두 가지고 있다면</p>
<pre class="angelscript"><code>seq 10
seq 11</code></pre>
<p data-ke-size="size16">중에서 <code>seq = 11</code>을 더 최신 record로 판단할 수 있다. 이 기능이 중요한 이유는 현실의 네트워크 환경에서 노드의 endpoint가 영원히 고정되어 있지 않기 때문이다. 특히 가정용 네트워크, 클라우드 환경, NAT 환경에서는 IP나 Port 정보가 변경될 수 있다.</p>
<h2 data-ke-size="size26">3. key/value</h2>
<p data-ke-size="size16">ENR의 나머지 데이터는 key/value 형태로 저장된다.</p>
<pre class="routeros"><code>"id"        -&gt; "v4"
"ip"        -&gt; IPv4
"tcp"       -&gt; TCP Port
"udp"       -&gt; UDP Port
"secp256k1" -&gt; Public Key</code></pre>
<p data-ke-size="size16">EIP-778에서 중요한 설계 중 하나가 바로 이것이다.</p>
<p data-ke-size="size16">새로운 정보가 필요해도 기존 ENR 구조 전체를 다시 설계할 필요가 없다.</p>
<pre class="lsl"><code>기존

고정된 필드 구조
↓
새로운 정보 추가가 어려움


EIP-778

key/value
↓
새로운 key를 추가할 수 있음</code></pre>
<p data-ke-size="size16">기존 구현체는 자신이 이해하지 못하는 key가 들어오더라도 record 형식 자체를 깨뜨릴 필요가 없다.</p>
<p data-ke-size="size16">그래서 EIP 문서에서는 이 구조가 향후 프로토콜 업그레이드와 cryptographic agility에 도움이 된다고 설명한다.</p>
<h3 data-ke-size="size23">RLP Encoding</h3>
<p data-ke-size="size16">ENR의 canonical encoding은 RLP(Recursive Length Prefix) 를 사용한다. </p>
<p data-ke-size="size16"> canonical Encoding은 이 데이터를 표현할 때 모두가 따라야 하는 인코딩 방식이다. ENR을 실제 바이트 데이터로 효현할 때는, RLP형식의 [ signature, seq, key, value, ...] 구조를 공식적인 표준 표현으로 사용한다는 뜻입니다.</p>
<pre class="json"><code>[signature, seq, k, v, ...]</code></pre>
<p data-ke-size="size16">EIP-778에서는 ENR의 최대 크기를 300 bytes로 제한한다.</p>
<p data-ke-size="size16">노드 record는 discovery나 DNS 같은 네트워크 메커니즘을 통해 전달될 수 있기 때문에 지나치게 큰 record가 계속 유통되면 비효율적이다.</p>
<p data-ke-size="size16">따라서 무제한으로 데이터를 집어넣는 구조가 아니라 크기 제한을 둔다.</p>
<h3 data-ke-size="size23">Text Encoding</h3>
<p data-ke-size="size16">ENR을 사람이 문자열로 전달해야 하는 경우도 있다. 이때 ENR은 RLP 인코딩 결과를 URL-safe Base64로 표현하고 앞에 <code>enr:</code> prefix를 붙인다. 형식은 다음처럼 보인다.</p>
<pre class="mercury"><code>enr:-IS4QHCYrYZbAKW...</code></pre>
<p data-ke-size="size16">그래서 Ethereum 관련 설정이나 네트워크 정보를 보다 보면 <code>enr:</code>로 시작하는 긴 문자열을 볼 수 있다.</p>
<p data-ke-size="size16">이는 단순한 랜덤 문자열이 아니라 하나의 노드 연결 정보를 표현한 Ethereum Node Record이다.</p>
<h3 data-ke-size="size23">ENR이 사용되는 전체 흐름</h3>
<p data-ke-size="size16">개념적으로 정리해보면 다음과 같다.</p>
<pre class="crmsh"><code>Node A
 │
 │ 자신의 연결 정보 생성
 │
 ▼
ENR
 ├─ signature
 ├─ seq
 ├─ public key
 ├─ IP
 ├─ TCP
 └─ UDP
 │
 │ 다른 Node에게 전달
 ▼
Node B
 │
 ├─ Signature 검증
 ├─ Sequence Number 확인
 └─ Endpoint 확인
 │
 ▼
Node A와 P2P 연결 시도</code></pre>
<p data-ke-size="size16">ENR은 그 자체가 Ethereum 블록이나 트랜잭션에 저장되는 데이터는 아니다. Ethereum의 P2P 네트워크 계층에서 노드들이 서로를 발견하고 연결 정보를 교환하기 위해 사용되는 표준이다. 이 점에서 EIP-1559처럼 블록이나 트랜잭션 처리 규칙을 바꾸는 Core EIP와 성격이 완전히 다르다.</p>
<h2 data-ke-size="size26">실제 사용 사례 - Geth에서는 어떻게 사용될까?</h2>
<p data-ke-size="size16">Geth란 Go Ethereum의 줄임말이며, 이더리움 프로토콜을 Go 언어로 구현한 대표적인 Execution Client이다. 쉽게 말하면 Ethereum Protocal -&gt; 실제로 실행할 프로그램 필요 -&gt; Geth 이다.</p>
<p data-ke-size="size16">Geth를 실행하면 해당 컴퓨터는 Ethereum 네트워크의 한 노드로 동작할 수 있다. 주요 역할은 </p>
<ul data-ke-list-type="circle" style="list-style-type: circle;">
<li>다른 Ethereum 노드와 P2P 연결</li>
<li>트랜잭션 수신 및 전파</li>
<li>블록 데이터 검증</li>
<li>EVM 실행</li>
<li>... 등등등</li>
</ul>
<p data-ke-size="size16"> 그래서 Ethereum 실행 클라이언트의 실제 구현을 보면, 대표적인 실행 클라이언트인 Geth(go-ethereum) 의 코드에는 ENR을 처리하기 위한 패키지가 실제로 존재한다. 예를 들어 Geth의 <code>p2p/enode/node.go</code>에서는 입력 문자열이 <code>enr:</code>로 시작하는지 검사한 뒤,</p>
<pre class="properties"><code>Base64 Decode
    ↓
RLP Decode
    ↓
ENR Record 생성
    ↓
Signature 검증</code></pre>
<p data-ke-size="size16">과정을 거쳐 Node 객체를 생성한다. Geth 코드의 로직을 단순화하면 다음과 같다.</p>
<pre class="stata"><code>if !strings.HasPrefix(input, "enr:") {
    return nil, errMissingPrefix
}

bin, err := base64.RawURLEncoding.DecodeString(input[4:])

var r enr.Record
err = rlp.DecodeBytes(bin, &amp;r)

return New(validSchemes, &amp;r)</code></pre>
<p data-ke-size="size16">그리고 <code>New()</code> 과정에서는 record의 signature를 검증한다. 즉 EIP 문서에 적혀 있는 ENR 형식이 단순한 이론으로 끝나는 것이 아니라 실제 Ethereum 클라이언트의 P2P 코드 안에서 사용되고 있다. Geth의 discovery 구현에서도 <code>p2p/enr</code> 패키지를 사용하며, Discovery v4 코드에는 다른 노드에게 최신 ENR을 요청하는 <code>RequestENR</code> 로직도 존재한다.</p>
<h2 data-ke-size="size26">Bootnode와 Peer Discovery</h2>
<p data-ke-size="size16">Geth를 처음 실행하면 이미 알고 있는 peer가 하나도 없을 수 있다. 그래서 초기 peer를 찾는 출발점 역할을 하는 것이 Bootnode이다. 대략적으로는</p>
<pre class="routeros"><code>Geth 실행
   ↓
Bootnode 접촉
   ↓
다른 Node 정보 획득
   ↓
Discovery Protocol 수행
   ↓
Peer Table 구성
   ↓
다른 Ethereum Node와 연결</code></pre>
<p data-ke-size="size16">의 과정을 거친다. 중요한 점은 ENR과 Node Discovery를 같은 개념으로 보면 안 된다는 것이다.</p>
<pre class="asciidoc"><code>Node Discovery
= 다른 노드를 찾는 프로토콜

ENR
= 발견한 노드의 연결 정보를 표현하는 데이터 형식</code></pre>
<p data-ke-size="size16">이라고 구분하면 이해하기 쉽다.</p>
<h1>정리</h1>
<p data-ke-size="size16">EIP-778은 Ethereum 노드의 P2P 연결 정보를 표현하기 위한 Ethereum Node Record(ENR) 표준이다.</p>
<p data-ke-size="size16">기존 Discovery v4에서는 노드가 전달할 수 있는 정보가 제한적이었는데, ENR은 이를 확장 가능한 key/value 형태로 만들었다.</p>
<p data-ke-size="size16">핵심을 정리하면 다음과 같다.</p>
<pre class="vbnet"><code>signature
→ record가 해당 node identity에 의해 만들어졌는지 검증

seq
→ 어떤 record가 더 최신인지 판단

key/value
→ IP, Port, Public Key 및 새로운 정보를 유연하게 표현

RLP
→ ENR의 canonical binary encoding

enr:
→ ENR의 text representation</code></pre>
